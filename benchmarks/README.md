# Litebook benchmark baseline

The suite measures the current matching engine before storage or batching refactors.
Rust and Python use the same event shapes and xorshift64 seed (0x5eed). Order UUIDs,
hash seeds, and wall-clock timestamps remain generated by the library as in normal use.

## Rebuild and validate

```shell
bash scripts/rebuild.sh -q
bash scripts/native.sh test --locked
bash scripts/native.sh clippy --locked --all-targets -- -D warnings --allow dead_code
bash scripts/native.sh bench --locked --bench book -- --test
uv run --no-sync python -m benchmarks.book --samples 2 --warmups 1 --batches 2
```

Run modules from the repository root. The native wrapper uses the virtualenv's
interpreter and runtime library directory, including for pyenv installations.
The extension is built in release mode; Criterion uses the optimized bench profile
with line debug information. LTO and CPU-specific optimization flags are unchanged.

## Record a comparison

```shell
bash scripts/native.sh bench --locked --bench book -- --warm-up-time 0.5 --measurement-time 1 --sample-size 20 --save-baseline stage1
uv run --no-sync python -m benchmarks.native_report --output benchmarks/results/native.json
uv run --no-sync python -m benchmarks.book --samples 7 --warmups 2 --batches 16 --latency --memory-events 60000 --output benchmarks/results/python.json
```

Run on an idle machine with the same CPU affinity, interpreter, compiler, build
flags, and workload parameters for each comparison. On Linux, prefix each command
with `taskset -c <allowed-cpu>` to pin it. Record from a committed tree: reports
include revision, tracked-change status, lockfile/source hashes, CPU, affinity,
interpreter/compiler versions, and the imported extension hash. The native report
also hashes the benchmark executable. Set a new Criterion baseline name when needed.

The recorded stage-one results and hardware details are in [BASELINE.md](BASELINE.md).
Raw Python samples, Criterion estimates/confidence intervals, and native raw samples
are checked into results/. Criterion's complete local output remains in target/criterion.

## Workloads

| Case | Seed state | Measured commands per fixture | Expected outcome |
| --- | --- | --- | --- |
| resting_existing/8 or /512 | One buy at each price level | 256 adds into existing levels | No fills |
| resting_new/256 | Empty | 256 adds at distinct buy prices | 256 new levels |
| cancel/16, /256, /4096 | One buy queue at the specified depth | Up to 256 distinct cancellations, shuffled with the fixed seed | Successful removal, including interior orders |
| partial/256 | One sell with quantity 257 | 256 unit buys | 256 positive partial fills; maker remains open |
| sweep/8 or /64 | One sell at each price level | One crossing buy | 8 or 64 fills; empty active book |
| mixed/64 | 64 buys across 8 levels | 64 cycles of 6 commands | 128 fills, 64 cancellations, 64 active orders |

Each mixed cycle adds and cancels a passive buy, adds a sell and a crossing buy,
then adds a buy and a crossing sell. This exercises both resting sides. Five of six
commands are submissions and one is a cancellation. Filled history grows even though
active depth stays fixed. These are controlled synthetic workloads; production-feed
replay remains a later extension of the suite.

## Timing boundaries

Criterion receives a fresh fixture through iter_batched_ref with LargeInput. UUID
creation, seeding, event construction, and final book destruction are outside native
timing. Moving prepared orders, matching, index updates, fill allocation/destruction,
cancellation, dispatch, and outcome counting are inside. Throughput counts submitted
commands, so one sweep command can produce many fills. Native fixture tests verify
positive fills and expected active state before performance is compared.

Python reports two modes. In precreated mode, order creation and seeding are outside
timing; the timed region includes the Python dispatch loop, argument extraction and
copying, Rust operations, Python fill-list/object conversion and destruction, and
outcome counting. In create-add mode, creating each submitted order, generating its
ID/timestamp, converting its price, and retaining its ID for later cancellation also
occur inside timing. Seed construction remains outside in both modes. Cancellation-only
cases perform no order creation in either mode.

Every sample processes independent fixtures, with validation afterward. Warmups are
excluded, timers are monotonic, and GC is disabled only during throughput timing.
Python reports raw durations and median/min/max ns per command. Its throughput samples
are aggregate timings, not per-event latency percentiles. The optional latency run uses
fresh fixtures and separate per-event timers, reports add/cancel percentiles, and includes
instrumentation overhead. It measures synchronous service time without queueing.

Memory replay runs in a separate fresh process with one long-lived book and a streaming
mixed workload. Linux VmRSS checkpoints measure approximate process resident memory;
unsupported platforms report null. The expected retained-filled count comes from the
trace and current retention contract. This isolates sustained growth from the large
pre-generated fixtures used for throughput; it is not an allocation profiler.

CI smoke checks validate outcomes and execution without enforcing speed thresholds.
The next profiling stage should measure allocations, cache behavior, and production traces.
